# Spec：健身记录与建议

> 状态：**ready-for-agent** · 创建 2026-11-12 · 成长循环的第二个载体
> 上游：[会成长的个人助手 spec](../growing-assistant/spec.md)。隐私三档、确认闸门、成长循环的约束以主 spec 为准，本文只写增量。

Status: ready-for-agent

## 问题（Problem Statement）

邮件那条线解决的是"别人交给我、我必须处理"的事；健身是另一条完全靠自觉的线。练了什么、这个动作这周比上周多了还是少了、下次该加重量还是该换动作，全凭记忆和感觉。网上的建议又不知道我的目标、一周只能练几天、膝盖有没有伤。结果是要么每次硬加重量然后卡住，要么干脆不练。

我要的是一个 30 秒能记完、点一下就能拿到"基于我自己记录、对得上我现实"的两三条建议的地方；我说一句"别每次都让我加重量，我一周只能练两次"，下次建议就真的按这个来。

## 方案（Solution）

手机端同一个页面新增「健身」tab，三块：

1. **记录**：7 个固定动作的表单（重量×次数×组数，可展开逐组）+ 一句话快捷输入（模型解析后回填表单，确认才保存）+ 每天一条体重 + 四个字段的训练画像。
2. **最近**：按日期倒序的训练、各动作容量、体重趋势。
3. **给我建议**：点一下才生成。脚本算事实与候选，模型只做措辞与排序；没有 API key 就出确定性模板。最多 3 条，每条 = 结论 + 支撑数据 + 一个具体动作；数据不够就直说。底部一个纠正输入框，记录后由 `hpa growth run` 固化，下次建议随之改变。

## 用户故事（User Stories）

1. 作为用户，我想在手机上 30 秒内记完一次训练，以便不因为麻烦而放弃记录。
2. 作为用户，我想只从固定的 7 个动作里选，以便不用每次打字、统计也不会因为叫法不同而分裂。
3. 作为用户，我想输入「80×5×5」就生成 5 组，以便快速记录。
4. 作为用户，我想展开逐组修改，以便某组少做或降重量时记录准确。
5. 作为用户，我想让自重动作只填次数，以便引体向上和悬挂举腿不被"重量"卡住。
6. 作为用户，我想一次训练里加多个动作，以便完整记录一次课。
7. 作为用户，我想保存后立刻在「最近」里看到这次训练，以便确认没记错。
8. 作为用户，我想删掉刚记错的一次训练，以便建议不被脏数据带偏。
9. 作为用户，我想每天填一次体重、重复填覆盖当天，以便看趋势又不被它绑架。
10. 作为用户，我想用一句话输入训练（如「深蹲 80kg 5组5次」），以便比表单更快。
11. 作为用户，我想让模型解析后先回填表单、由我确认才保存，以便解析错了不会直接入库。
12. 作为用户，我想在没有模型 key 时也能解析常见格式，以便断网或没配 key 时也能记。
13. 作为用户，我想设置目标、每周可练天数、器械、伤病，以便建议对得上我的现实。
14. 作为用户，我想在画像没填完整时被明确告知缺什么，以便不拿到瞎猜的建议。
15. 作为用户，我想只在点「给我建议」时生成，以便不被推送和排期打扰。
16. 作为用户，我想最多拿到 3 条建议，以便能执行而不是被淹没。
17. 作为用户，我想每条建议都有结论、数据和**一个**具体动作，以便知道为什么、也知道下一步做什么。
18. 作为用户，我想建议里的数字全部来自我自己的记录，以便不被模型编造的进步或退步误导。
19. 作为用户，我想数据不够时被直说「再记 N 次才能判断」，以便知道是数据少而不是我不行。
20. 作为用户，我想在没有模型时也有确定性的建议，以便核心功能不依赖外部服务。
21. 作为用户，我想建议对齐「一周只能练两次」，以便不被建议一周练三次。
22. 作为用户，我想看到建议的生成时间和它依据的规则，以便判断是否过时。
23. 作为用户，我想用一句话记录纠正，以便不用写长文。
24. 作为用户，我想固化后用同一份数据得到不同的建议，以便感到它真的在学我。
25. 作为用户，我想纠正只改偏好、话术、目标，以便数值阈值不被模型悄悄改掉。
26. 作为用户，我想固化前建议保持不变，以便行为可预期、能对照。
27. 作为用户，我想一键灌 4 周演示数据、又能一键清掉，以便验收演示不污染真实记录。
28. 作为用户，我想在同一个页面切换邮件与健身、刷新后还停在上次的 tab，以便操作连贯。
29. 作为用户，我想训练备注只留在本机、永不进 prompt，以便敢写真实感受。
30. 作为用户，我想结构化的训练记录与画像可以进 prompt，以便建议真的基于我的数据。
31. 作为用户，我想按本地日期划分「本周」，以便半夜记录不会串到上一周。
32. 作为用户，我想回看最近若干次训练和体重趋势，以便自己也能判断，而不只依赖建议。

## 实现决策（Implementation Decisions）

### 领域模型与数据

- **动作**：固定 7 个，存稳定英文 ID，UI 显示中文名。部位映射固定：平板卧推/窄距卧推→胸，引体向上→背，二头弯举→二头，深蹲/硬拉→腿，悬挂举腿→核心。
- **组**：一行一组，存 `exercise + set_index + weight_kg + reps`。输入「80×5×5」展开为 5 行同重量同次数；展开后可逐组改。自重动作 `weight_kg` 为空。
- **容量**：某动作 Σ（重量×次数）；自重动作以总次数计，不参与吨位比较。
- **体重**：一天一条，以本地日期唯一，重复提交覆盖当天。只作背景趋势，不单独出建议。
- **训练画像**：单一真相是 `memory/training-profile.md`，文件头固定四行键值（目标 / 每周可练 / 器械 / 伤病），其余自由文字保留。UI 只改这四行；解析缺字段或失败时画像标记为不完整，建议里明说缺什么。目标取值：力量 / 增肌 / 减脂 / 维持 / 未设定；每周可练：1–7 的整数。
- **时间**：所有周窗口按本地时区（Asia/Shanghai）的日期划分；存 `performed_on`（YYYY-MM-DD）用于归桶，另存开始时间用于显示。
- **表**：`workouts`（id、performed_on、started_at、note、is_demo、created_at）、`workout_sets`（id、workout_id、exercise、set_index、weight_kg、reps）、`weight_logs`（id、logged_on、weight_kg、is_demo）、`advice_runs`（id、created_at、payload JSON、llm_used）。`corrections` 加 `scope`（`mail` / `fitness`，默认 `mail`），健身纠正的 `message_id` 为空。
- **迁移**：启动时建新表；`corrections` 用 `ALTER TABLE ... ADD COLUMN` 补 `scope`，旧行按 `mail` 处理。
- **删除**：训练物理删除并级联删组；UI 二次确认，服务端要求请求体带 `confirm: true`，否则拒绝。体重不单独删，覆盖即可。
- **保留**：建议运行保留最近 20 条，超出不显示但可清理。

### HTTP 接口（沿用现有 `/api/state` + POST 分发 + token 保护）

| 接口 | 契约 |
| ---- | ---- |
| `GET /api/state` | 新增 `fitness`：画像（含 `complete` 与缺失项）、最近训练（含各动作组与容量）、体重趋势、上次建议、待固化纠正数 |
| `POST /api/fitness/parse` | `{text}` → `{draft, uncertain[], parser: "rules"|"llm"|"none"}`；只解析，不写库 |
| `POST /api/fitness/record` | `kind` = `workout` / `weight` / `profile`；分别写入训练（含嵌套动作与组）、当天体重、画像四行 |
| `POST /api/fitness/advice` | 生成并保存一次建议，返回建议载荷 |
| `POST /api/fitness/correct` | `{note}` → 写 `corrections`（scope=fitness），返回「已记录，等固化」 |
| `POST /api/fitness/workouts/<id>/delete` | `{confirm: true}`；删除一次训练及其组 |

- 校验：动作必须在 7 个之内；重量 0–500 kg（自重为空）；次数 1–100；组数 1–20；日期不得晚于今天；备注长度上限（如 500 字）；快捷输入上限 300 字。
- 写接口一律要求 token（复用现有校验）；`GET /api/state` 同现有规则。

### 建议引擎

- **输入**：最近 4 个滚动 7 天桶（含当前不完整桶，标「本周至今」）的训练与组、体重趋势、训练画像、`rules/fitness-advice.md`。
- **三条规则**（v1）：
  1. **频率 / 部位间隔**：同一部位两次训练间隔 < 48h；最近 7 天训练次数低于画像的每周目标（或高于目标过多）。
  2. **容量趋势**：某个动作的周容量连续 2 周下降 > 10%，或单周上升 > 30% 时提示；持平不在这里报，交给停滞规则。
  3. **进步停滞**：某动作 3 周内最好一组（按 Epley 估算 1RM；自重动作按最好一组的次数）没有提升，且周容量也没有增长（±5% 内或下降），期间至少练了 3 次。evidence 同时给周容量序列与最好一组。停滞候选的动作随「每周可练」调整：每周 >2 天时建议尝试加重量，≤2 天时保持重量；画像缺失时不猜，按保守动作并写进 `insufficient`。
- **脚本产出候选**：每条候选带 `rule`、`workout_ids`、脚本文本化的 `evidence`（含日期与数字）、严重度分数。每条规则最多贡献 1 条（取该规则下最严重的一条），总共最多 3 条，避免三条建议都在说停滞。停滞候选同分时按最近 4 周公斤容量降序，自重动作排后；演示数据下深蹲（2.0t）胜出。
- **模型只做两件事**：在候选之间排序、给每条写「结论 + 一个动作」。模型输出 `{order: [候选 id], texts: {id: {conclusion, action}}}`；服务端按 id 合并脚本文本化的 `evidence`。`order` 不是候选 id 的完整排列时按脚本分数排序。模型文本里不允许出现数字，出现数字即回退模板——数字只能来自脚本。
- **无模型 / 模型失败**：用候选类型对应的确定性模板生成结论与动作，`llm_used=false`，UI 标注「本地规则」。
- **输出契约**：`{generated_at, llm_used, items: [{rule, conclusion, evidence, action, workout_ids}], insufficient: ["再记 N 次…"]}`；`items` 最多 3 条，可以为 0 条（全部数据不足时）。
- **数据不足**：训练日期少于 2 天，或某动作少于 3 次，相关候选不生成，理由进 `insufficient`。
- **画像对齐**：频率规则直接用「每周可练天数」；画像缺失时不猜，把缺口写进 `insufficient`。
- **体重**：只出现在「最近」的趋势里，不进入建议条目。

### 快捷输入

- 先用本地正则解析标准格式（动作名 + 重量 kg + 次数 + 组数，支持 `×`/`x`/`*`/「组」「次」）；解析成功不回模型。
- 本地解析失败才调模型，要求输出与表单同构的 JSON 和 `uncertain` 字段；模型失败则返回 `parser: "none"`，表单留空提示手填。
- 任何情况下 `parse` 都不写库，写库只走用户确认后的 `record`。

### 成长循环（扩展，不新建循环）

- `growth.run` 按纠正的 `scope` 分流：`mail` 完全走现有逻辑（回归不能变）；`fitness` 用另一份固化提示，产出两类提案：
  - `rule` → 追加到 `rules/fitness-advice.md`（带「来源：纠正 #N」注释）；
  - `profile` → `{key, value}` 结构化更新训练画像的四个键之一（目标 / 每周可练 / 器械 / 伤病），**改写文件头对应行，不新增重复行**；若同一句话还含可执行偏好，可额外带一条 `rule`，一并追加（Q15 的“别默认加重量 + 一周两次”即此情况）。
- `fitness` 的合法目标是 `rules/fitness-advice.md` 与 `memory/training-profile.md`；后者 `kind` 必须是 `profile`，否则拒绝。
- 健身纠正的上下文 = 纠正原文 + 训练画像 + 最近 4 周摘要 + 上次建议；**绝不拼训练备注**（P1）。
- 固化提示明确：只改偏好 / 话术 / 目标；不得改代码、不得改数值阈值、不得删既有规则。
- 建议生成时拼装 `rules/fitness-advice.md` + 画像 + 结构化训练摘要（P0）；备注永不进 prompt。

### 演示种子

- `hpa demo seed`：写入 4 周、每周 1 次训练，四个动作各按验收数据（深蹲 80kg×5×5、平板卧推 60kg×5×5、引体 8×3、悬挂举腿 12×3），另加每周一条体重（75kg）；画像：力量 / 每周 3 天 / 健身房 / 无伤。全部 `is_demo=1`。
- 幂等：先清 demo 再灌；`hpa demo seed --clear` 只删 `is_demo=1` 的训练与体重，不碰真实记录。
- 拒绝混入：库里已有非 demo 的训练时，`seed` 默认拒绝并提示换独立数据目录，避免污染真实统计。UI 在存在 demo 数据时显示「演示数据」横幅与清除入口。

### 手机端

- 同一页加「邮件 / 健身」两个 tab，无路由；上次 tab 存浏览器 localStorage，刷新后恢复。
- 「健身」tab 自上而下：记录表单（含一句话输入）、最近记录与体重趋势、建议区（按钮 + 最近一次结果 + 纠正输入框）。
- 生成中显示状态；模型失败或未配置时明确标注「本地规则」；备注输入旁标「仅本机，不进模型」。
- 不做图表库，趋势用文字与简易条形。

## 测试决策（Testing Decisions）

**什么算好测试**：只断言外部行为——HTTP 的 JSON 契约、CLI 退出码与文件内容、prompt 里出现/不出现什么；不测私有函数、不锁具体文案。时间与模型都可注入，断言数字与结构，不断言模型的自由发挥。

**接缝**（已与用户确认）：

1. **HTTP JSON（主接缝）**：用现有 `make_server` 起真实 server，走 `/api/state` 与 `/api/fitness/*`。注入 FakeLLM 的方式与现有 sender 注入对齐（`llm_factory`）。
   - 一条端到端验收测试：设画像 → 记 4 周训练 → 请求建议（≤3 条、每条 evidence 带数字、引用 workout id）→ 记纠正 → `growth.run` → 再请求建议（画像驱动 2 天；规则进入模型措辞上下文）。
   - 无 LLM key / 模型抛错时仍返回 200 且 `llm_used=false`。
   - 校验用例：未知动作、越界次数、未来日期、缺 token、删除不带 `confirm`。
   - 隐私用例：备注写入后，捕获发给模型的 system/user 文本，断言不含备注原文。
   - 快捷输入：本地正则命中、模型命中、全失败三条路径。
   - 删除：训练删掉后组也没了，建议不再引用它。
2. **`growth.run`（既有接缝，扩展）**：FakeLLM 返回健身目标提案，断言规则文件追加且带来源注释；`profile` 提案改写文件头那一行而不是追加重复行；`message_id` 为空时上下文含画像与 4 周摘要、不含备注；非法目标/非法 kind 被拒；邮件纠正路径回归不变。
3. **`hpa demo seed`（小接缝）**：灌种子后 4 周数据齐全、深蹲周容量恰为 2.0t；再灌一次不翻倍；有真实记录时拒绝；`--clear` 后真实记录仍在。

**既有先例**：HTTP 用 `tests/test_send_web.py`、`tests/test_web_actions.py`；FakeLLM 用 `tests/test_growth.py`、`tests/test_pipeline.py`；组合链路用 `tests/test_export_daemon.py`。

**规则数学**（4 周窗口边界、48h 间隔、10%/30% 阈值、3 周停滞）通过主接缝 + 固定种子日期覆盖，不另开纯函数接缝；边界用例超过 6 个再拆。

UI 不做浏览器自动化（与现有仓库一致），只手工验收。

## 不在范围内（Out of Scope）

- 饮食、睡眠、体脂、围度、心率、Apple 健康导入。
- 自定义动作库、「新增动作」按钮（7 个先跑一段时间再说）。
- 训练计划生成、自动排期、推送提醒。
- 均衡（推/拉/腿是否都练到）与恢复（睡眠/疲劳）规则——v2。
- RPE/RIR、1RM 实测、周期化。
- 编辑历史训练（v1 只能删除重记）。
- 检索 vault（v2 仅在用户问「为什么」时按需检索一次）。
- 多用户、账号体系、云端同步。
- 图表库、复杂动画。

## 补充说明（Further Notes）

### 验收脚本（对应 Q15）

1. `hpa demo seed`，起 `hpa web`，手机切到「健身」tab。
2. 点「给我建议」：3 条以内，其中一条指出深蹲周容量连续 3 周停在 2.0t（或进步停滞），一条对齐「每周 3 天」；每条都带日期/数字和一个动作。
3. 在纠正框写：「别每次都让我加重量，我一周只能练两次」。
4. 电脑上 `hpa growth run`：`rules/fitness-advice.md` 追加一条规则，`memory/training-profile.md` 的「每周可练」改成 2；`git diff` 可审。
5. 回手机再点「给我建议」：同一份数据，建议不再默认「加重量」，频率按 2 天算。
6. 演示完 `hpa demo seed --clear`，真实记录不受影响。

### 演示种子与阈值

- 深蹲 80×5×5 = 2000kg = 2.0t/周，连续 4 周 → 容量持平 + 进步停滞两条都成立，用于演示「同一份数据、纠正前后建议不同」。初始画像每周 3 天，纠正后变 2 天，频率建议随之改变。
- 阈值写死在代码常量里：48h、10%、30%、3 周、4 周窗口。纠正改不了它们；要改只能改代码并跑测试（见主 spec 的成长循环约束）。

### 隐私表（补主 spec 第 7 节）

| 档位 | 内容 | 处理 |
| ---- | ---- | ---- |
| P0 | 训练记录、体重、训练画像（结构化） | 可进 prompt，用于生成建议 |
| P1 | 训练的自由文本备注 | 只在本机 SQLite，**永不进 prompt、永不进日志** |

### 风险与对策

| 风险 | 对策 |
| ---- | ---- |
| 模型在建议里编数字 | 数字只由脚本生成 evidence，模型文本出现数字即回退模板 |
| 画像文件被手改坏，规则层解析失败 | 固定四行键值 + 容错解析；不完整就明说，不猜 |
| 建议变成通用鸡汤 | 只上 3 条规则，每条必须引用 workout id 与数字；数据不够宁可不给 |
| 记录负担导致弃用 | 一句话输入 + 默认「重量×次数×组数」；30 秒目标写进验收 |
| 演示数据混进真实统计 | 有真实训练时 `seed` 拒绝写入；`is_demo` 标记 + UI 横幅；演示后 `seed --clear` 一键清 |
| 与邮件链路抢同一 SQLite | 单进程单连接串行写；新表不改旧表语义（仅加 `scope` 列） |
