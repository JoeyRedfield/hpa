# Spec：会成长的个人助手

> 状态：**草案 v0.1**，待你审阅 · 创建 2026-11-11 · 对应 [docs/lab1.md](../../docs/lab1.md) 的改编版
> 本文是 `.scratch/growing-assistant/` 下的规格；tickets 会从第 9 节的里程碑拆出。

## 0. 已锁定的决策

| 决策 | 结论 |
| ---- | ---- |
| 个人数据库载体 | 直接索引现有 Obsidian vault `~/Documents/notes`，**不复制资料** |
| 对 vault 的写权限 | **只读**；助手自己的规则/记忆/状态写在本项目 |
| 主线流程 | 邮件 → 待办 → 草稿 → 手机确认 → 发送 → 归档 |
| 邮箱 | **QQ 邮箱**（IMAP + 授权码），先只接一个 |
| 手机端 | 本地 Web / PWA，经 **Tailscale** 访问 |
| 部署 | 本机 Mac 常开 |
| 运行时 | Python 脚本管确定性流程；LLM（DeepSeek）只负责"理解" |
| 主动性 | 后台轮询 + 有新事推提示；**一切对外动作过确认闸门** |
| "成长" | 优先做**规则**与**记忆**，技能（固化脚本）后置 |
| 与 Lab 原文偏差 | 无 smail/ehall 账号，按作业精神用真实邮箱与真实事务替代，README 已声明 |

## 1. 范围

**做**：邮件增量拉取与幂等去重、邮件理解与分类、待办抽取、回复草稿生成、手机端确认与编辑、SMTP 发送、笔记库全文检索与原文定位、纠正→规则→生效的成长闭环。

**不做**（明确排除，避免长成 AI slop）：
- 不做通用聊天机器人，不提供聊天窗口
- 不做日历/通讯录同步、不做附件 OCR、不做多邮箱
- 不自动发送、不自动删除/归档邮件（无人类确认时）
- 不把 vault 内容回写进 vault（只读）
- 不训练/微调模型，成长靠规则与记忆文件

## 2. 用户故事（验收时演示这一条）

> 早上 9:07 收到一封"XX 项目验收安排"的邮件。
> 9:12 助手已把它变成：待办「周三前回复验收时间」+ 一份草稿「确认出席，附上周进度」。
> 你在手机上看到草稿，把它从"确认出席"改成"申请改到周四"，点确认。
> 邮件发出，发出的正是你改过的版本。
> 你顺手记一笔纠正：「以后这类会议安排邮件，默认先问我时间是否冲突，不要直接答应」。
> 这条纠正在下一封同类邮件上生效。

## 3. 架构

```
┌────────────────────────── Mac（常开） ──────────────────────────┐
│                                                                  │
│  daemon (python, asyncio)                                        │
│   ├─ scheduler ──每 5 分钟─→ mail_sync ──→ sqlite ──┐            │
│   │                                   │              │           │
│   │                                   ▼              │           │
│   │                            triage (rules→LLM)    │           │
│   │                                   │              │           │
│   │                        ┌──────────┴───────┐      │           │
│   │                        ▼                  ▼      │           │
│   │                     todos             drafts     │           │
│   │                                                  │           │
│   └─ http server (127.0.0.1:8787, FastAPI) ◄─────────┘           │
│         ▲                                                        │
│         │ Tailscale                                              │
└─────────┼────────────────────────────────────────────────────────┘
          │
    📱 手机浏览器 / PWA（待办 · 草稿编辑 · 确认 · 纠正）
```

- **进程只有一个**：`uv run hpa daemon` 同时跑调度器与 HTTP 服务，避免两个进程抢状态。
- **外部依赖最小**：`imaplib`/`smtplib`/`sqlite3` 都是标准库；只有 HTTP 服务与 LLM 客户端是第三方包。
- **失败要能回滚**：状态机每一步落盘，进程重启后从 `state/` 恢复，不重放已完成动作。

## 4. 数据与目录

```
hpa/
├── README.md                  # intent
├── GLOSSARY.md                # 领域词表
├── docs/                      # lab 原文、侦察、ADR、agent 配置
├── .scratch/growing-assistant/ # spec + tickets
├── config.toml                # 非敏感配置（邮箱地址、轮询间隔、模型名）
├── rules/                     # ★ 成长产物：规则即 Markdown，人可读可改
│   ├── mail-triage.md
│   └── reply-style.md
├── memory/                    # ★ 成长产物：偏好与事实（key→value 的 md）
├── prompts/                   # LLM 系统提示（拼装 rules + memory）
├── src/hpa/
│   ├── daemon.py              # 入口：调度器 + HTTP 服务
│   ├── config.py
│   ├── store.py               # sqlite 封装（索引 / 状态 / 待办 / 草稿）
│   ├── adapters/mail_imap.py
│   ├── pipeline/triage.py     # 规则优先，LLM 兜底
│   ├── pipeline/draft.py
│   ├── pipeline/send.py
│   ├── pipeline/kb.py         # vault 索引与检索（FTS5）
│   └── web/                   # 单页 PWA（无构建步骤，原生 JS）
├── state/                     # ★ 不入库：游标、邮件原文缓存、草稿、纠正日志
├── .cache/kb.sqlite3          # 可重建的知识库索引
└── tests/
```

**入库边界**：`state/`、`.cache/`、`.venv/`、`secrets.env` 全部 gitignore；`rules/`、`memory/`、`prompts/`、`src/`、`tests/` 入库。

### 数据表（SQLite）

| 表 | 主键 | 用途 |
| -- | ---- | ---- |
| `messages` | `message_id` | 已见过的邮件（幂等去重），存 uid/日期/发件人/主题/摘要 |
| `todos` | `id` | 待办：来源邮件、标题、截止时间、状态 `open/done/dropped` |
| `drafts` | `id` | 草稿：关联 message、正文、状态、确认时间 |
| `corrections` | `id` | 用户纠正的原始记录（追加写，永不改） |
| `kb_docs` | `path` | vault 文件：mtime、大小、标题、tags |
| `kb_fts` | — | FTS5 虚表：正文分词，用于检索与原文定位 |

**幂等三条硬规则**：
1. 邮件以 `Message-ID` 去重；IMAP 游标用 `UIDVALIDITY + UID`，不用"最新 N 封"。
2. 草稿以 `(message_id, 版本)` 唯一；发送前再查一次 `drafts.status`，`sent` 的永不再发。
3. 发送用"先置 `sending` 再真发，成功后 `sent`，异常置 `failed`"的两阶段状态，崩溃后不重复发。

## 5. 关键流程：邮件 → 待办 → 草稿

1. **同步**（每 5 分钟）：IMAP 取 UID > 游标的新邮件 → 过滤发件人黑名单 → 写 `messages`（重复则跳过）。
2. **分类**（规则优先）：先跑 `rules/mail-triage.md` 里的确定性规则（发件人/主题关键词/是否含 `unsubscribe`/是否是我自己的地址）；规则未命中才调 LLM，输出 JSON `{needs_reply, is_fyi, confidence, why}`。
3. **抽取**：对 `needs_reply` 或 `is_fyi` 的邮件，LLM 抽 `{todos[], deadline, entities[], kb_queries[]}`。
4. **检索**：用 `kb_queries` 查 FTS5，取 top-k 段落，附路径与标题（**原文定位**：`path#标题` 或 `path:行号`）。
5. **起草**：LLM 生成草稿，风格由 `rules/reply-style.md` + `memory/` 决定；草稿里引用资料时保留来源标记。
6. **推送**：草稿进 `drafts`，手机页面出现待办卡片与草稿。
7. **确认**：你在手机上编辑 → 点「发送」→ 服务端把**确认时的正文**作为唯一发送内容（不重新生成）。
8. **发送与落账**：SMTP 发送 → `sent` → 记 `sent_at`；UI 显示已发，附发出正文快照。

## 6. 成长循环（这个项目的核心）

```
你纠正一句 ──→ corrections（追加记录）
                    │
                    ▼
        固化成 rules/*.md（人可读、可改、进 git）
                    │
                    ▼
     下一轮 prompt 拼装时注入（全部规则 + 相关记忆）
                    │
                    ▼
        tests/rules/ 里的样例邮件 → 断言行为改变（回归）
```

- **一次纠正必须落成文件**，不能只留在对话里——这是 Lab 原文点名的那条要求。
- 规则文件有固定格式：一句话规则 + 为什么 + 反例（见第 9 节 M4）。
- **可验证**：每条规则至少配一条样例邮件与期望判定，`pytest tests/rules` 能证明"新会话仍生效"。

## 7. 隐私三档

| 档位 | 内容 | 处理 |
| ---- | ---- | ---- |
| **P0 可发模型** | 普通笔记、项目文档、课程资料 | 全文索引，可进 prompt |
| **P1 身份/私密** | `vault/private/` 下的个人信息、党建材料 | **只索引标题与 frontmatter，不索引正文**；正文永不进 prompt；填表时由本地脚本注入明文 |
| **P2 凭证** | 密码、邮箱授权码、API key、cookie | 存 `~/.config/hpa/secrets.env`（chmod 600），**永不入库、永不进 prompt、永不进日志** |

> ⚠️ P1 的索引范围是本 spec 唯一没锁死的点，见第 10 节。

## 8. 手机端（最小可用）

一页搞定，不做多页面导航：

- **待办区**：今日需处理，可勾完成/忽略
- **草稿区**：正文可编辑、显示引用来源、底部两个按钮「发送」「丢弃」
- **纠正区**：一句话输入框，提交后落到 `corrections` 并提示「已记录，等固化」
- **状态条**：上次同步时间、邮箱健康状态、今日 token 用量

技术要求：`127.0.0.1:8787` 绑定，Tailscale 内网访问；单页 HTML + 原生 JS；加 `manifest.json` 可添加到主屏；不做登录（Tailscale 已提供身份边界），但写操作要求一个本地 token（存 `secrets.env`），防止同机其他程序误调。

## 9. 里程碑与验收

| 里程碑 | 内容 | 验收（可演示） |
| ------ | ---- | -------------- |
| **M1 知识库** | vault 增量索引 + FTS5 检索 + 原文定位 | 随机问 10 个关于自己笔记的问题，命中正确笔记并给出 `path#标题` |
| **M2 邮件接入** | IMAP 增量拉取、幂等去重、规则分类 | 连跑 3 次同步，`messages` 不增；能列出"今日 5 封需处理" |
| **M3 草稿与确认** | LLM 草稿、手机编辑、SMTP 发送 | 改过的草稿发出内容 = 改后版本；重复点发送只发一封 |
| **M4 成长闭环** | 纠正 → 规则 → 新会话生效 + 回归测试 | 给一条纠正，重启进程后同类邮件行为改变，`pytest tests/rules` 通过 |
| **M5 组合与归档** | 邮件→检索→草稿→发送→归档一条完整链路 | 完整复现第 2 节用户故事，全程在手机完成 |

每个里程碑结束：README 更新「效果」一节 + `git commit` + 记一条 ADR（若做了架构决策）。

## 10. 待你拍板的三个点

1. **`vault/private/` 索引到什么程度**（第 7 节 P1）：只索引标题 / 连正文一起索引但不进 prompt / 完全不索引。
2. **待办与草稿归档去哪**：只留在本项目 `state/`；还是每周导出成一份 Markdown 放进 vault（需你手动或确认后由你操作）。
3. **纠正的固化方式**：由我（agent）把纠正改写成 `rules/*.md` 再给你确认；还是你在手机上直接写规则原文。

## 11. 风险与对策

| 风险 | 对策 |
| ---- | ---- |
| QQ 邮箱 IMAP 授权码未开/失效 | M2 第一步就实机验证；失败则退到网页自动化或换邮箱 |
| LLM 分类误判导致漏掉重要邮件 | 规则兜底 + 每天一次的"漏网检查"（列出未生成草稿的邮件让你扫一眼） |
| 草稿质量差反而增加负担 | 先只对"明确需要回复"的邮件起草；草稿必须显示依据来源 |
| 状态损坏导致重复发送 | 两阶段发送状态 + `sent` 不可逆 + 发送前二次查询 |
| 单机常驻服务被误调用 | 写操作 token；只绑 127.0.0.1，靠 Tailscale 提供网络边界 |
| 长成 AI slop（Lab 的警告） | 每个里程碑收敛范围；不适用的功能显式写进"不做" |
